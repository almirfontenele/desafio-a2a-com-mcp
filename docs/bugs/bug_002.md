## 1. Sumário Executivo & Descrição do Problema

Durante a auditoria arquitetural de conformidade com os requisitos mandatórios descritos no documento [docs/desafio.md](file:///home/almir/projetos/desafio-a2a-com-mcp/docs/desafio.md) (Seção *Tecnologias Obrigatórias*), foram identificadas duas não conformidades críticas na infraestrutura e no empacotamento do projeto:

1. **Implementação Ad-Hoc do Servidor MCP sem o SDK Oficial**:
   O servidor MCP ([servidor-mcp/server.py](file:///home/almir/projetos/desafio-a2a-com-mcp/servidor-mcp/server.py)) foi construído artesanalmente sobre a biblioteca padrão `http.server.HTTPServer` e `BaseHTTPRequestHandler`, implementando manualmente o despacho JSON-RPC em vez de utilizar o **SDK oficial do MCP v2** em Python (pacote `mcp` >= 1.0 / revisão da spec `2026-07-28`), exigido explicitamente pelo enunciado do desafio.
2. **Ausência de Manifesto com Dependências Travadas (`pyproject.toml`)**:
   O repositório não dispõe de arquivo `pyproject.toml` nem `requirements.txt` declarando as versões pinadas (`==`) das bibliotecas utilizadas.
3. **Inconsistência no [Dockerfile](file:///home/almir/projetos/desafio-a2a-com-mcp/Dockerfile)**:
   A imagem Docker instala pacotes externos (`mcp`, `fastapi`, `uvicorn`) sem restrição de versão (`pip install --no-cache-dir mcp uvicorn fastapi...`), e esses pacotes não chegam a ser consumidos no código-fonte, gerando código morto no container e risco de quebras de compilação/execução decorrentes de atualizações upstream.

## 5. Comportamento Observado vs. Comportamento Esperado

### 5.1 Comportamento Observado (Actual Behavior)
- O servidor MCP foi implementado manualmente através de um despachante JSON-RPC próprio sobre `http.server.BaseHTTPRequestHandler`.
- Não há definição de `pyproject.toml` para controle formal de dependências do ecossistema Python.
- As dependências listadas no `Dockerfile` não possuem versões fixadas e instalam pacotes (`fastapi`, `mcp`) que não são utilizados pela implementação manual.

### 5.2 Comportamento Esperado (Expected Behavior)
- O servidor MCP deve ser construído sobre o **pacote `mcp` oficial do Python**, suportando os handlers de ferramentas (`tools`), recursos (`resources`) e elicitation de MRTR (`input_required`).
- O projeto deve conter um arquivo `pyproject.toml` padronizado (PEP 517/518/621) com todas as dependências pinadas em versões fixas.
- O `Dockerfile` deve instalar as dependências diretamente a partir do manifesto do projeto, garantindo reprodutibilidade estrita de build.
- A conformidade do validador ([validador/validar.py](file:///home/almir/projetos/desafio-a2a-com-mcp/validador/validar.py)) deve ser mantida com 36/36 verificações aprovadas.

## 7. Análise de Causa Raiz (Root Cause Analysis - RCA)

1. **Localização**:
   - [`servidor-mcp/server.py`](file:///home/almir/projetos/desafio-a2a-com-mcp/servidor-mcp/server.py) — Ausência de integração com o SDK oficial `mcp`.
   - Raiz do repositório — Ausência de `pyproject.toml`.
   - [`Dockerfile`](file:///home/almir/projetos/desafio-a2a-com-mcp/Dockerfile) — Declaração solta de pacotes no `pip install`.

2. **Mecanismo da Falha**:
   - A especificação do desafio ([docs/desafio.md](file:///home/almir/projetos/desafio-a2a-com-mcp/docs/desafio.md)) estipula como tecnologia obrigatória: *"SDK oficial do MCP na v2, alinhado à revisão 2026-07-28 da spec: (...) o pacote mcp do Python (3.10 ou superior)"* e *"Versões travadas no package.json ou no pyproject.toml"*.
   - A implementação inicial optou por construir um servidor HTTP customizado via biblioteca padrão para simular a resposta Streamable HTTP, deixando de alavancar o SDK oficial e desconsiderando a exigência de governança de dependências do projeto.

3. **Fatores Contribuintes**:
   - O validador ([validador/validar.py](file:///home/almir/projetos/desafio-a2a-com-mcp/validador/validar.py)) testa o comportamento externo no protocolo JSON-RPC/HTTP (caixa preta) e aprova 36/36 verificações mesmo com o servidor artesanal; porém, os critérios de entrega e avaliação do enunciado penalizam a falta do SDK e a ausência do `pyproject.toml`.

## 8. Proposta de Correção e Mitigação (Fix & Mitigation Plan)

### 8.1 Plano de Ação

1. **Criar o arquivo `pyproject.toml`**:
   - Declarar metadados do projeto (`name`, `version`, `requires-python = ">=3.10"`).
   - Travar todas as versões de dependências necessárias:
     ```toml
     [project]
     name = "desafio-a2a-com-mcp"
     version = "1.0.0"
     description = "A Ponte: Agente A2A com MCP por dentro"
     requires-python = ">=3.10"
     dependencies = [
         "mcp>=1.2.0,<2.0.0",
         "uvicorn[standard]==0.30.6",
         "fastapi==0.115.0",
         "starlette==0.38.6",
         "requests==2.32.3",
         "httpx==0.27.2",
         "aiohttp==3.10.5",
         "pydantic==2.9.2"
     ]
     ```

2. **Reescrever o Servidor MCP com o SDK Oficial**:
   - Migrar o servidor HTTP para uma aplicação ASGI baseada no SDK `mcp` (ex.: `mcp.server.lowlevel` ou `mcp.server.fastmcp`), expondo os endpoints `/mcp` e `/reset`.
   - Mapear as tools (`listar_salas`, `consultar_disponibilidade`, `reservar_sala`) e resources (`politica://uso`) através das anotações e tipos do SDK.
   - Manter a lógica determinística de domínio de [servidor-mcp/mcp_rules.py](file:///home/almir/projetos/desafio-a2a-com-mcp/servidor-mcp/mcp_rules.py) e [servidor-mcp/mcp_security.py](file:///home/almir/projetos/desafio-a2a-com-mcp/servidor-mcp/mcp_security.py).

3. **Adequar o [Dockerfile](file:///home/almir/projetos/desafio-a2a-com-mcp/Dockerfile)**:
   - Modificar o estágio de instalação para instalar as dependências através do manifesto:
     ```dockerfile
     COPY pyproject.toml /app/
     RUN pip install --no-cache-dir .
     ```

### 8.2 Cuidados de Arquitetura e Invariantes
- [x] **Compatibilidade com o Validador**: O endpoint Streamable HTTP `/mcp` e o endpoint auxiliar `/reset` devem preservar estritamente os contratos e respostas esperados pelo [validar.py](file:///home/almir/projetos/desafio-a2a-com-mcp/validador/validar.py).
- [x] **Determinismo**: Manter 0% de uso de LLM ou APIs probabilísticas.
- [x] **Ciclo MRTR**: Assegurar integridade e opacidade do token `requestState` selado com HMAC-SHA256.
